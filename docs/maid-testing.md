# 女仆验收测试体系（maid-testing）

> 目的：女仆的行为规程全写在 `task-brain` skill 里，但"写了"不等于"做到了"。本体系把手册变成可执行的考卷，对每一代女仆做可复现的验收。

## 三层架构

| 层 | 测什么 | 断言方式 | 运行成本 |
|---|---|---|---|
| **L1 反射层** | 单跳条件反射（问句→查回话、定跳留痕、default 15 分钟、每跳留痕防死循环） | 机械断言（正则/JSON 字段），全自动 | 秒级，可离线 |
| **L2 场景层** | 职责域场景（晨间唤醒/每日任务/出行硬日程/摸鱼检测/触达选道/守夜） | 剧本 + 断言清单（部分自动、部分人工核对） | 需要主人配合演一轮 |
| **L3 人格层** | 病娇浓度、渴望感、嗔怪语气 | 多轮对话后按清单打分（1-5 × 权重） | 最贵，3 次试验取均分 |

通过标准：L1 必须 100%；L2/L3 每个用例喂 3 次，全部通过或通过率 ≥90%。

## 关键设计原则

1. **断言标注 spec 来源**：每条断言对应 skill 的某一节（§1步骤4/5 等）。手册改了哪节，立刻知道哪些用例受影响——测试是手册的镜像。
2. **职责域 = 套件文件**：L2 按 skill §4 的职责域分 `tests/suites/*.json`（morning / daily-tasks / travel / slacking / reach / night），新增职责 = 新增一个 json，框架不动。
3. **失败样本即新用例**：女仆每翻一次车，在对应 suite 加一条"上次怎么死的"变体——同一个坑永不二跌。
4. **历史会话 = 免费题库**：12~31 号的失败会话全部保留，L1 可对它们做离线回归，训练效果一测便知。

## 用法

```powershell
# L1 离线回归:对全部历史女仆会话跑反射层断言
node scripts/maid-test.mjs l1 --all-sessions

# 对单个会话跑
node scripts/maid-test.mjs l1 --session C:\Users\Dao\.dsh\sessions\--C-Users-Dao-anima-home--\session-xxxx

# 列出可测会话
node scripts/maid-test.mjs list

# 手册自身的静态体检（重复概念/近似重复句/孤儿引用/废机制残留/双副本一致）
# 语义与阈值见 maintenance.md「audit 的语义：棘轮，不是理想值」
node scripts/maid-test.mjs audit
```

当前 L1 断言原语（新增断言往 maid-test.mjs 加 check 函数）：

| 断言 | spec | 判据 |
|---|---|---|
| R1 问句→下一跳安排查回话 | §1步骤4/铁律 | assistant 消息含"？" → 其后第一条排钟的 title/prompt 含"回话/回音/答案/追问/报数/回复/等到" |
| R2 定跳留痕 | §1步骤5 | 每条排钟（含 at 档）的**字条标题**须能看出「何时+干什么」：含时间锚点（HH:MM / M-D / 明早 / 窗口 / 分钟…），且去掉锚点后还剩 ≥3 字事由（"noop"、"23:15 采样" = 违规） |
| R3 每跳必须留痕 | §1步骤5 | 以 turn 为一跳：排了钟的那一跳必须有 assistant 台词/值班短记（一整跳只有 reasoning+工具调用、一个字没留 = 违规） |
| R4 生命线不断档 | §1步骤5/睡眠安全 | 硬红线只有一条：**删了钟必须当场补**（同 turn 内必须出现新的排钟）。节奏快慢由女仆自己定，评估器不替她判断 |

> 节奏不写断言，改成**参考信息**打印：每个会话头部输出 `节奏分布`（900s×N、1800s×N、at×N…）。15 分钟是兜底不是天花板，"她这次自己挑了什么节奏"是给人看的，不是判分项。

## 解析层（2026-10-06 修，重要）

评估器**不再读 maid-log 的人读文本**，改走 `node maid-log.mjs <会话> --raw`（每行一个完整事件 JSON、不截断），因为：

- 旧版按 600 字符截断的行去正则匹配，`"state":"scheduled"` 常被切掉——实测长会话 144 次排钟只认出 **1 次**，R2/R3 因此长期空转（"55/80"是假分）。
- schedule 工具的返回早已从 `afterSeconds` 变成 `{"kind":"every","everySeconds":900}` / `{"kind":"at"}`，且 `schedule_update` 与 `schedule_create` 返回同一结构，必须两种都算"排了钟"。
- 真实返回文本住在 `data.message.content[].text` 里；直接 `JSON.stringify(data)` 会把引号转义成 `\"`，正则匹配不到。

## L2/L3 流程（人工配合）

1. 从对应 suite 选一个变体，读它的**剧本**（主人怎么演：何时回话、何时装睡）。
2. 新建女仆会话，按剧本注入提示词（主人粘贴）。
3. 结束后跑 `l1 --session <dir>` 看机械断言，再按 suite 的**人工核对清单**逐条打分。
4. 结果记入 suite 文件的 `trials` 数组（3 次一轮），通过率 ≥90% 该变体过关。

**2026-10-05 重构后（历史记录）**

- 10 秒链式跳机制已按主人决定移除（女仆用不习惯，改为回话驱动：问句→下一跳查回话→追问一次→收兵）。R1 断言随之改为"下一跳字条安排查回话"。
- 新增 §1 末尾"今日时刻表"——每跳先扫表定位该干什么，治提醒心不在焉。
- 性格收拢为三色合一（撒娇/病娇/强势），语气规则与三色挂钩。
- **节奏定为兜底制（2026-10-06 主人决定）**：废除多档采样率（盯梢 3-10 分钟 / 平常 15 / 外出 90 / 查证 1-5）。最终口径是——**15 分钟周期钟（`every_seconds: 900`）只作"防止出错"的兜底**（装一次就一直响，哪一跳断了也不会失联）；**日常闹钟的节奏由女仆自己按需要定**（盯紧要数字就缩短、外出就拉长、有节点或主人给了时刻就用 `at` 定点），唯一要求是把理由写进字条。所以 R4 不再管快慢，只守"删了必须当场补"这条生命线红线；变化改由 R3 约束"每跳必须留痕/换动作"。
- 评估器已知局限：（1）R2/R3 是**按会话全或无**判定（一条空字条就让整个会话不过），适合当"红线"用，要看严重程度读违规条数；（2）"at 钟响过必须补下一条"这条 doctrine **离线测不到**（日志结束可能只是因为那条 at 还挂着），只能靠会话里肉眼核。
